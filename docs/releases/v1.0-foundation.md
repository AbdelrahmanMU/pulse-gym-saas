## 1. Freeze declaration & change control

The following are **frozen** as of Foundation v1.0:
- The **architecture** (modular monolith, feature-sliced; tenancy model; module boundaries; ownership).
- The **data model** (DDS) and the **Prisma schema** (validated under Prisma 7).
- The **design system** (PULSE v1.1, tokens, component catalog).
- The **engineering governance** (workflow, standards, AI rules).
- The **domain rules** (business rules, invariants, state machines, money/time/immutability).

**Change-control rule (binding):**
1. A **breaking architectural change** — anything that alters an ADR decision, a business invariant, the tenancy model, the data model's shape/ownership, the authorization model, or a frozen standard — **requires an ADR update**: a new/superseding entry in `decision-log.md` (and the relevant ranked doc) with **human approval**, per CLAUDE.md §11/§13.
2. **Non-breaking, additive evolution** (new feature specs under `docs/features/`, additive migrations, new permission keys, new components) follows the normal development workflow and does **not** require re-freezing — but still updates the single owning doc (no duplication).
3. **Permission keys are never renamed** (INV-7); **shipped migrations are never edited** (database-standards); **history is never mutated** (immutable-history).
4. Conflicts are resolved by the **Documentation Hierarchy** (CLAUDE.md §12) and **Conflict Resolution** (§13): docs outrank code; higher-ranked docs outrank lower; uncertainty → STOP and ask.

> In short: **the foundation changes only through an approved ADR.** Implementation lives *within* it.

## 3. Locked technical decisions (snapshot)

The binding details live in the cited docs; this is the at-a-glance lock list.

| Area | Decision | Source |
|---|---|---|
| Architecture | Modular monolith, feature-sliced; modular monorepo (Turborepo + pnpm); MVP ships only `web` | ADR-001/002/015 |
| Stack | Next.js 15 · TypeScript (strict) · Tailwind v4 + shadcn via PULSE · PostgreSQL 18 · **Prisma 7** · Zod · Auth.js · Docker Compose | ADR-003…006/016, ADR-027 |
| Identifiers | **UUID v7**, native `uuid` (`@db.Uuid`); not CUID/serial/v4 | ADR-026, identifier-strategy |
| Tenancy | Every business row `gym_id` (+ `branch_id`); query-scoped by session `gym_id` | ADR-007, DDS |
| Authorization | **Permission-based, never role-based**; dormant roles seeded unassignable | ADR-013/014 |
| Money | Integer minor units (`BigInt`) + currency (`Char(3)`); never floats | DDS §8, money-rules |
| Time | UTC stored; judged in gym tz; inclusive end day | DDS §9, time-rules |
| History | Append-only ledgers/periods; void not edit; soft-delete; derived-not-stored | DDS §11, immutable-history |
| Lifecycle | Deferred upgrade (Scheduled successor); status controls access, not payment standing | ADR-018/019/021 |

## 4. Bootstrap entry point
With this release frozen, implementation begins at **Sprint 0 / Bootstrap** per `docs/engineering/implementation-strategy.md`: scaffold the monorepo, generate the initial migration from `initial-migration-specification.md` (incl. the raw-SQL tail), run the seed (incl. the reserved `system-actor` User), then proceed Auth → Authz → Members → Plans → Memberships → Payments → Dashboard → Notifications → Reporting → Release Candidate. Each feature obeys this frozen foundation; any deviation is an ADR change, not an implementation choice.
