# Decision Note — Should a freeze auto-resume on its planned end date?

**Date:** 2026-07-02
**Branch:** `feat/platform-foundation`
**Type:** Lifecycle / product-design decision note — **open question for the Beta backlog.** No code.
**Owning report for:** **TD-18** (registered in
[technical-debt-report](../releases/v1.0-rc-review/technical-debt-report.md)).
**Status:** Recommendation made; **awaiting human ruling** (lifecycle change = human's call,
constitution §8/§11). Nothing implemented.

---

## The question

Today a **FROZEN** membership stays frozen until a staff member explicitly clicks **Resume**. If the
planned unfreeze date passes and nobody acts, the membership remains FROZEN and **keeps accumulating
frozen days**, continuously pushing the end date out. Should the system instead **auto-resume** the
membership when the freeze's planned end date arrives?

## How freeze/resume actually works today (grounding)

- **FROZEN is derived, not stored.** `deriveMemberLifecycle` marks a membership FROZEN purely because
  an **open (`ACTIVE`) freeze row exists** (`lifecycle.ts:74-75`). Status is a live derivation off that
  row; nothing is time-triggered.
- **Resume is a *write* that finalizes money/time, not a status flip.** Resuming **closes the freeze
  row** — sets `actualEnd`, flips `status = ENDED`, and **finalizes `frozenDays` (INV-18)**, which is
  what extends the membership end date (FRZ). Source of truth: `MembershipFreeze` is append-only
  history; *"Resume closes the row (sets actual_end / status=ENDED)"* (`schema.prisma:507-517`).
- **`plannedEnd` is nullable.** Freezes may be **open-ended** (medical / travel with unknown return),
  in which case there is **no date to auto-resume on**.
- **The app has no scheduler.** Every derived value is computed **on read**, and even notifications are
  generated by an **on-page-open server action**, not a background job (**TD-8**). There is no cron,
  worker, or queue anywhere in the app.
- **Resume records a human actor** (`endedById`) — the audit trail names who resumed.

## The failure mode this is trying to fix (real)

A **forgotten freeze**. Nobody resumes on time → the membership stays FROZEN → frozen days keep
accruing → the end date drifts ever further out. The member gets an unearned extension and the gym
loses paid-for time. This is a genuine operational gap worth closing.

---

## Options

### Option A — Keep resume manual, add a "resume due" operational cue *(recommended for Beta)*
Do **not** auto-execute. Instead surface **"Freeze past its planned end — resume due"** as an alert
(a notification and/or a flag in the member workspace Overview) so a human resumes deliberately.

- ✅ **Zero new architecture** — reuses the existing on-open notification generation and the
  planned member-workspace surface (see
  [member-centric-workspace review](./product-architecture-review-member-centric-workspace.md)).
- ✅ **Preserves the write-on-resume model** — `frozenDays`/`actualEnd`/end-date extension are still
  finalized by an explicit action, keeping INV-18 and the append-only history intact.
- ✅ **Preserves the human audit actor** (`endedById`).
- ✅ **Works for open-ended freezes too** — an open-ended freeze that's dragged on can still be flagged
  by age, even with no `plannedEnd`.
- ⚠️ Doesn't *eliminate* the manual step — it makes forgetting visible instead of automatic.

### Option B — True auto-resume via a scheduled reconciliation job *(the "real" auto-resume; after Beta)*
A **nightly lifecycle-reconciliation job** closes every freeze whose `plannedEnd` has passed —
writing `actualEnd = plannedEnd`, `status = ENDED`, finalizing `frozenDays`, with a defined **system
actor**.

- ✅ Matches member expectation ("froze for 30 days → back on day 31") with no staff action.
- ✅ Caps the end-date drift at the *planned* duration — arguably **more correct** than a forgotten
  manual resume that over-extends.
- ❌ **Requires scheduler infrastructure the app deliberately doesn't have** — a new dependency +
  pattern (constitution §9: not without human approval). Shares the exact infra need as **TD-8**
  (notification generation → worker/cron); the two should be decided together.
- ❌ **Only applies to freezes with a `plannedEnd`** — open-ended freezes still need Option A's cue, so
  B never fully replaces A.
- ❌ **New audit semantics** — introduces a non-human `endedById` (system actor) into freeze history.
- ❌ Removes the human "should we really resume now?" checkpoint (e.g. member still injured).

### Option C — Pure-derivation "auto-resume" (treat as resumed once `plannedEnd` passes, no write)
Rejected. FROZEN can be *derived*, but the freeze's **end-date extension must be persisted** — you
cannot finalize `frozenDays` (INV-18) or extend the period without a write. Deriving "resumed" while
leaving the extension unwritten makes the end date ambiguous and breaks the append-only freeze model.
This is not a viable read-model-only shortcut.

---

## Recommendation

**Beta: Option A.** It closes the actual pain (forgotten freezes silently over-extending) at the
lowest risk, needs no new architecture, and preserves the lifecycle invariants and audit trail. It
also slots directly into the member-workspace roadmap already proposed.

**After Beta: consider Option B** as a deliberate, separately-scoped feature — decided **together with
TD-8**, since both need the same worker/cron capability and a defined system actor. Even if B ships,
Option A's cue remains necessary for **open-ended** freezes.

**Do not** pursue Option C.

## What needs a human ruling

1. Accept **Option A for Beta** (build the "resume due" cue), or defer entirely?
2. Is auto-resume (Option B) a desired **post-Beta** direction, to be bundled with the TD-8
   scheduler decision — or should freezes always require an explicit human resume?
3. If B is ever pursued: what is the **system-actor** identity for `endedById`, and should auto-resume
   apply only to freezes with a `plannedEnd` (yes, by construction)?

**No lifecycle behavior changes without a ruling on the above.**
